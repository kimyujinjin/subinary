# 가족 자산 V2 — 수동 기록 계약

이 기능은 직접 입력한 자산 값과 주택 지급 기록을 보관한다. 은행·증권 연결, 자동 이체, 투자 매매, 대출 실행, 시가/수익률 추정, 외화 환산은 수행하지 않는다. 기존 카드 거래·예산·자산이동 분류는 별도 계약으로 유지한다. 마이그레이션 `0065_manual_finance`는 코드로만 추가했으며 운영 DB에 적용하지 않았다.

## 소유·공유와 조회 범위

- 모든 요청은 인증된 사용자와 해당 가족의 활성 멤버십을 요구한다. 기록 작성자의 멤버십도 활성 상태여야 조회할 수 있다.
- `ownerUserId`는 작성·수정·공유 변경 권한을 가진 계정이다. 검증된 법적 명의나 공동 지분을 뜻하지 않는다. `legalOwnerLabel`은 사용자가 직접 적은 표시이고 미입력이면 `null`이다.
- 기본 `visibility`는 `private`이다. `household`로 명시 변경한 기록만 가족에게 보인다. 가족 소유자·관리자 역할도 타인의 개인 기록을 조회하거나 수정할 수 없다.
- `scope=private`는 본인의 개인 기록만, `scope=household`는 명시 공유 기록만 반환한다. 목록·상세·합계·다음 지급 일정은 같은 허용 집합을 사용한다. 보이지 않는 항목 수, 숨겨진 금액의 차액, 타인 개인 기록의 존재를 응답으로 알려주지 않는다.
- 작성은 `owner|admin|member` 역할의 활성 구성원만 할 수 있고, 수정·공유 변경·삭제는 그중 기록 작성자만 할 수 있다. `viewer`는 조회 전용이며 본인 기록이 남아 있어도 쓰기 요청은 403으로 거부하고 DTO의 `canEdit=false`로 표시한다. 가족 소유자·관리자 역할도 타인의 개인 기록 권한을 덮어쓰지 않는다. 타인 개인 기록의 상세와 타인 기록의 수정·삭제는 존재를 구분할 수 없는 응답으로 처리한다. 명시 공유된 타인 기록은 조회할 수 있다.
- 가족 구성원 제거 시 그 사용자의 공유 수동 자산·주택 계획을 같은 트랜잭션에서 개인으로 바꾸고 버전·메타데이터 감사를 남긴다. 재가입해도 공유가 자동 복구되지 않는다. 조회 시 작성자 활성 멤버십 조건도 유지한다.

구성원 제거는 가구의 기존 멤버십 행을 ID 순서로 잠근 뒤 트랜잭션 안에서 행위자의 활성 상태·역할과 최후 소유자 조건을 다시 검사한다. 잠금 대기 중 제거되거나 권한을 잃은 행위자의 이전 판정으로 다른 구성원을 제거하지 않는다. 소유자 두 명의 동시 탈퇴도 마지막 활성 소유자 한 명을 남겨야 한다. 공유 철회 후 캐시 갱신 힌트는 커밋 뒤 최선 노력으로 보내며, 개인 기록만 있는 경우 수동 기록 활동을 알리는 힌트를 보내지 않는다.

실시간 연결은 연결 시점과 각 hint/heartbeat 전 활성 멤버십·미삭제 사용자·미삭제 가족을 검사한다. 최초 멤버십의 ID와 PostgreSQL `xmin`을 고정해 같은 행이 탈퇴·재가입으로 재활성화되어도 옛 연결을 재사용하지 않는다. 역할·색상 등 멤버십 행 수정도 기존 연결을 닫고 재인증하게 하는 보수적 동작이다. 검증된 JWT 만료와 연결 후 15분 중 먼저 도달하는 시각에 종료한다. DB 확인 실패는 활동 정보를 전달하지 않고 연결을 종료한다. 이미 인가 확인을 마쳐 전송 중이던 이벤트와 탈퇴 커밋 사이의 일반적인 경합까지 동기적으로 회수하는 보장은 아니다.

문자 수집 동의 철회(`/households/:id/privacy/consent/revoke`)와 가족 멤버십 제거는 별개다. 전자는 기존 수집 장치·동의를 철회하며 수동 기록의 공개 범위를 자동 변경하지 않는다. 수동 기록의 공유 취소는 작성자의 공개 범위 변경 또는 가족 멤버십 제거 경로를 따른다.

## 자산 값과 합계

`kind`는 `account`(현재 잔액), `saving`(현재 기록 잔액), `stock`(직접 입력한 평가액), `loan`(남은 원금)이다. 대출 원금은 양수 부채로 기록한다. 실행되지 않은 대출 한도, 적금 만기 예상액, 주식 처분 예상액을 현재 현금으로 생성하지 않는다. 한 기록은 한 현재 스냅샷이며 자동 내역·복식부기 원장이 아니다.

금액은 KRW만 허용한다. JSON에서는 `"0"` 또는 선행 0 없는 1~20자리 양의 정수 문자열을 사용하고, DB는 `numeric(20,0)`, 계산은 `BigInt`를 사용한다. JS `number`, 소수, 지수, 음수, 쉼표 포함 금액은 요청 계약에서 거부한다. 미입력 `null`과 명시 입력 `"0"`은 다르다. 합계는 여러 기록을 더하므로 입력 한도 20자리를 넘을 수 있다.

금액이 있으면 실제 달력 날짜 `asOfDate`와 `source='manual'`이 필요하다. 금액이 없으면 기준일·출처도 `null`이다. 기준일은 SQL `date`/`YYYY-MM-DD`로 저장하고 서울 기준 오늘 이후를 거부한다. `source`의 화면 문구는 ‘직접 입력’이다. 계정·가입일 등 알려지지 않은 날짜를 오늘로 채우지 않는다. 기록 이름 외 nullable 표시·메모는 미입력이면 빈 문자열 대신 `null`로 보낸다.

자산 목록 응답의 `summary`는 다음 의미를 갖는다.

| 필드 | 의미 |
| --- | --- |
| `grossAssets`, `debt` | 각각 알려진 자산·부채의 부분합. 해당 집합에 행이 없거나 모든 값이 미입력이면 `null` |
| `assetsCompleteness`, `debtCompleteness` | `empty`: 행 없음, `partial`: 하나 이상 미입력, `complete`: 해당 집합의 모든 값 입력 |
| `completeness` | 전체 행 없음은 `empty`. 자산·부채 양쪽 집합이 모두 `complete`여야 `complete`, 나머지는 `partial` |
| `netAssets` | 양쪽 집합이 모두 `complete`일 때만 자산 합−부채 합. 부채 행 없음은 부채 0원으로 추정하지 않음 |
| `asOfDate` | 모든 값이 입력됐고 기준일이 하나로 같을 때만 그 날짜 |
| `oldestAsOfDate`, `newestAsOfDate`, `mixedAsOfDates` | 입력된 기준일 범위와 혼합 여부. 서로 다른 날짜의 입력을 하나의 시점 값으로 표시하지 않음 |

집계 함수는 사전에 인가된 한 scope의 행만 받는다. 같은 ID의 동일 스냅샷이 중복 전달돼도 한 번만 합산하며, 같은 ID의 값 충돌은 거부한다. 주택 계약·지급액은 자산·순자산 합계에 더하지 않는다.

## 주택 계획과 지급 기록

계획은 `label`, nullable `occupancyYear`, nullable 직접 입력 `contractStage`, nullable `fundingNote`, 공유 범위를 보관한다. 재원 메모는 용도 기록이다. 통장 ID 배정, 자금 예약, 부족액·현금 전망 계산, 주택 시가 평가를 수행하지 않는다.

지급 종류는 `contract`(계약금), `interim`(중도금), `balance`(잔금), `option`(옵션)이다. 회차(`installment`), 예정일(`dueDate`), 예정 금액(`amount`), 지급액(`paidAmount`), 실제 지급일(`paidDate`)은 각각 미입력일 수 있다.

- 지급액을 입력하려면 예정 금액이 필요하며 `0 ≤ paidAmount ≤ amount`이어야 한다. 지급액이 양수면 실제 지급일이 필요하다. 지급액이 미입력/0이면 지급일은 `null`이다.
- 예정일은 미래여도 된다. 실제 지급일은 서울 기준 오늘 이후일 수 없다. 지급 완료 여부를 미입력에서 추정하지 않는다. 명시된 예정액과 지급액이 같으면 완료로 볼 수 있으며, 둘 다 명시 `"0"`인 경우와 둘 다 `null`인 경우는 다르다.
- 계획과 전체 지급 배열(최대 100개)은 부모 계획 버전 CAS 하나의 트랜잭션으로 생성·수정한다. 각 지급 ID는 중복될 수 없고 입력 순서를 보존한다. 원자적 교체 중 실패하면 부모·자식·감사 모두 롤백한다.
- 지급 기록을 변경하거나 지급했다고 표시해도 카드 거래, 통장 잔액, 대출 잔여 원금은 자동 변경하지 않는다.

주택 목록의 `summary.nextPayment`는 **입력된 미지급 일정 중 가장 이른 행**이다. 과거에 예정됐으나 미지급으로 입력된 일정도 포함한다. 예정액·지급액·예정일이 모두 알려졌고 잔액이 양수인 행만 후보로 삼는다. 날짜가 같으면 계획 ID·지급 ID 순으로 결과를 고정한다. 자금 예측이나 전체 계약의 ‘다음 확정 지급’으로 설명하지 않는다. 계획에 지급 행이 없거나 어느 행의 예정액·지급액·예정일이 미입력이면 `hasIncompletePayments=true`를 함께 표시한다. 보이지 않는 계획은 이 상태에도 영향을 주지 않는다.

## 요청·동시성·감사

기본 경로는 `/v1/manual-finance/assets`, `/v1/manual-finance/housing-plans`이다. 목록은 `householdId`와 `scope`를 받는다. 자산 생성/상세/수정 응답은 `{item}`, 자산 목록은 `{items,summary}`이다. 주택 생성/상세/수정 응답은 `{item,payments}`, 주택 목록은 `{items,summary}`이다. 상세 DTO의 `canEdit`도 서버에서 계산한다.

생성은 클라이언트가 한 사용자 동작에 고정한 UUID `id`를 보내며, 재시도는 같은 ID와 원래 정규화 입력을 사용한다. DB의 `creationPayloadHash`는 최초 입력 SHA-256이고 응답으로 노출하지 않는다. 같은 ID의 다른 입력은 충돌이며 기존 기록·권한을 노출하지 않는다. 수정은 불변 ID/가구/작성자 없이 전체 수정 필드와 `expectedVersion`을 보낸다. 잠금 안에서 멤버십·작성자·행 버전·삭제 상태를 다시 확인한다. 경합한 옛 버전은 덮어쓰지 않는다.

목록·상세는 `repeatable read` 트랜잭션으로 계획과 자식 조회의 일관성을 유지한다. 쓰기는 `read committed`에서 활성 작성자 멤버십 `FOR SHARE OF household_members` → 살아 있는 가구 `FOR SHARE` → 본인 리소스 `FOR UPDATE` → 지급 자식 순서로 잠근다. 멤버십 조회에는 계정 미삭제 조건도 적용한다. 주택 생성 재시도에서 기존 부모와 자식을 읽을 때도 부모 공유 잠금을 유지한다. DB 오류에 포함될 수 있는 SQL 바인드·입력값은 사용자 응답이나 Nest 예외 로거에 전달하지 않고 일반 오류로 감싼다.

삭제도 작성자의 `expectedVersion` CAS를 사용한다. 자산/계획의 `deletedAt`을 기록하고 버전을 올리는 soft delete이다. 삭제된 계획의 자식은 모든 조회에서 제외한다. 같은 생성 UUID 재전송으로 삭제 기록을 되살리지 않는다. UI는 삭제 대상과 영향에 대한 확인을 받는다.

`manual_finance_audit`에는 가구·행위자·대상 식별자, `create|update|delete|membership_removed`, 버전, 시각만 보관한다. 금액·이름·명의·메모·요청 원문을 복제하거나 로그로 남기지 않는다. 변경과 감사는 같은 트랜잭션이며 `(entityType,entityId,version,action)`은 유일하다. 이 감사에 내부 사용자 식별자가 남으므로 익명 정보라고 주장하지 않는다.

버전이 PostgreSQL 정수 최댓값 `2147483647`에 도달한 기록은 일반 수정·삭제 요청을 거부한다. 다만 가족 탈퇴에 따른 공유 철회가 버전 초과 때문에 막히면 안 되므로 철회는 이 값에서 포화시켜 `private`으로 전이한다. 같은 최댓값의 기존 `update` 감사와 새 `membership_removed` 감사는 다른 사건으로 함께 남긴다. 작업 종류를 포함한 감사 유일 키는 이 개인정보 철회가 기존 수정 감사와 충돌해 탈퇴 전체를 롤백하는 일을 막는다. 제거 뒤 재가입해도 공유가 부활하지 않으며, 최댓값 기록의 일반 쓰기는 계속 거부한다.

## 검증과 운영 경계

`0065`는 `manual_assets`, `manual_housing_plans`, `manual_housing_payments`, `manual_finance_audit` 네 테이블을 추가한다. 새 `removeMember`는 테이블이 비어 있어도 이를 참조하므로 스키마 적용·journal·테이블 및 제약 확인 후 API를 배포하고 웹을 반영한다. 마이그레이터는 SQL 폴더/journal이 없으면 정상 종료할 수 있어 종료 코드만으로 적용 성공을 판단하지 않는다. 다른 미적용 마이그레이션을 함께 승인한 것으로 해석하지 않는다.

새 수동 기록을 사용하기 시작한 뒤에는 원래 `a0d3f6d` API를 그대로 롤백 대상으로 사용하지 않는다. 그 버전에서 멤버십을 제거·재가입하면 이전 `household` 공유 값이 남아 새 API 복귀 시 다시 조회될 수 있다. 이는 원래 `private` 기록이 자동으로 공개되는 경로와 다르다. 롤백 API에도 원자적인 수동 공유 철회·감사·멤버십 잠금과 실시간 재인가 보호를 포함해야 한다. 모든 API 인스턴스가 이 계약을 지켜야 하며, 롤백 시 새 스키마·기록을 역삭제하지 않는다. 호환 롤백 이미지와 최종 코드의 실제 HTTP/JWT·PostgreSQL·Redis 검증을 배포 전 별도 증거로 확인한다.

순수 정책·요청 계약·마이그레이션 정합성 검사는 합성 입력만 사용한다.

```sh
pnpm --filter @family/contracts build
node --test packages/contracts/test/manual-finance.test.mjs
pnpm --filter @family/shared exec vitest run src/manual-finance.test.ts
node --test packages/database/test/manual-finance.test.mjs packages/database/test/migrations.test.mjs
```

마이그레이션 검사는 추가형 SQL, journal 등록, schema와 제약 이름 일치, nullable 값·서울 날짜·지급 제약을 검사한다. 정적 SQL 검사가 실제 PostgreSQL 제약 실행이나 API 잠금·경합 통합 검증을 대체하지 않는다. 전체 API/화면·동시성·실제 DB 통합은 각 별도 검증 결과로 보고한다. 운영 DB 마이그레이션·데이터 변경·배포는 이 문서 작성으로 실행되지 않는다.

일반 soft delete와 가족 탈퇴 시 공유 중단은 개인정보 완전 파기/내보내기 구현을 뜻하지 않는다. 신규 수동 기록·명의 표시·메모·감사의 보관·내보내기·파기 연동은 별도 정책과 검증이 필요하다. 기존 개인정보 화면의 안내만으로 새 데이터까지 완전히 파기·내보내기된다고 약속하지 않는다.
