# 토스증권 계좌 연결 — 로컬 구현과 운영 활성화 조건

이 문서는 `fma-finance-connections`의 독립 변경을 설명한다. 기존 리뉴얼 배포와 별도다. 작성 시점에 실제 키 입력, 공급자 인증/조회, 운영 설정 변경, 0067 적용, 운영 배포는 하지 않았다. 자산 화면에 본인 연결 계좌 요약과 **연결관리** 진입을 두고, 상단 설정에서도 연결관리로 이동한다. 추가 하단 탭을 만들지 않는다.

## 지원 범위

- 본인 앱 계정으로 토스증권 클라이언트를 등록하고, 공급자가 돌려준 종합매매 계좌 중 하나를 직접 선택한다. 배우자는 배우자의 앱 계정으로 별도 등록한다. 계좌 명의의 법적 일치는 공급자 응답으로 증명되지 않으며 본인 계좌 확인은 사용자 진술이다.
- 앱에 키·조회 결과를 저장하고 자산 또는 연결 화면을 열 때 갱신한다는 동의를 각각 확인한다. 이 동의는 가족 공유나 금융사 약관 수락을 대신하지 않는다.
- 초기 버전은 소유자만 본다. 다른 가족 구성원·가족 관리자에게 목록, 잔액, 종목, 합계, 존재 여부를 반환하지 않는다. 가족 합계/수동 자산/기존 거래/주택 계획을 수정하지 않으며 중복 합산하지 않는다.
- 자산 또는 연결 화면을 열 때 한 번 또는 연결 화면에서 사용자가 새로고침할 때 조회한다. 두 화면은 동일한 ConnectionScreen 제어부와 최초 진입 갱신 경로를 사용한다. 자산의 요약 표현에는 별도 조회 상태·쓰기 버튼·갱신 타이머가 없다. 권한 재확인 GET은 공급자 재조회를 유발하지 않는다. 최소 간격은 연결당 60초다. 공급자가 `Retry-After`를 보내면 별도 `retry_not_before`에 보관하며 다음 가능 시각은 이 시각과 기본 60초 중 늦은 쪽이다. 실제 시도 시각을 미래로 바꾸지 않는다. 스케줄·worker 반복 실행·별도 자동화는 없다. 기기를 닫아 둔 동안 계속 추적한다고 표현하지 않는다.
- 국내·미국 주식만 지원한다. KRW와 USD 합계를 각각 그대로 표시한다. 두 통화는 환산값이 아니며 합산하지 않는다. Decimal과 int64를 JS Number로 바꾸지 않는다. 부호도 공급자 값 그대로 보존한다. 토스뱅크 현금·예금·채권·파생상품·신한/국민 계좌 연동을 제공한다고 표시하지 않는다.
- `observedAt`은 앱이 응답을 받은 시각이고 `valuationAt`은 null이다. 평가 기준 시각·환율·은행 기준일을 추정하지 않는다. 실패 시 마지막 성공 관측과 실패 상태를 함께 보존하며 금액을 0으로 바꾸지 않는다.

공식 근거는 [Toss Securities OpenAPI 1.2.28](https://openapi.tossinvest.com/openapi-docs/latest/openapi.json)와 [개발 가이드](https://developers.tossinvest.com/docs)다. 고정 호스트의 token/accounts/holdings만 허용한다. Toss Payments나 비공개 웹 API가 아니다. 클라이언트당 새 토큰 발급은 이전 토큰을 무효화하므로, 이 앱 밖의 도구에서 같은 클라이언트를 동시에 사용하면 재인증이 필요할 수 있다. 조회 메서드만 사용한다고 공급자 키 자체의 권한이 읽기 전용이 되는 것은 아니다. 개인 앱의 지속 키 보관·가족 표시/재배포·무료 요금 조건은 확인 완료로 간주하지 않았다. 운영자가 실제 적용 조건을 확인하기 전 활성화하지 않는다.

## API 계약

인증은 기존 앱 JWT 경로를 사용한다. 모든 응답은 `Cache-Control: no-store, private`다. GET은 금융사 접근이나 토큰 발급을 하지 않는다.

| 경로 | 입력과 동작 |
| --- | --- |
| `GET /v1/finance-connections?householdId=…` | `{enabled, disabledReason, items}`. 해당 사용자·현재 가족 멤버십 회차의 연결과 마지막 성공 관측만 반환 |
| `POST /v1/finance-connections/toss` | `householdId, connectionId, clientId, clientSecret, consent`. `connectionId`는 등록 멱등 ID. 세 동의는 `ownAccount`, `storeCredentials`, `refreshOnOpen` 모두 true |
| `POST /v1/finance-connections/:id/account` | `householdId, expectedVersion, accountId`. 서버가 공급자 목록에서 만든 불투명 ID만 선택 가능. 한 계좌여도 자동 선택하지 않음 |
| `POST /v1/finance-connections/:id/refresh` | `householdId, expectedVersion, requestId`. 성공/실패/진행 중을 영속 요청 기록으로 구분. 같은 요청 ID를 다시 보내도 금융사 조회를 반복하지 않음 |
| `DELETE /v1/finance-connections/:id` | `householdId, expectedVersion`. 앱에 저장한 암호화 키·토큰·공급자 계좌 매핑을 폐기하고 앞으로의 접근 차단 |

등록의 같은 ID/같은 키는 현재 상태를 반환한다. 같은 ID에 다른 키를 넣으면 충돌이며 키를 교체하지 않는다. 해제된 등록 ID는 다시 활성화되지 않는다. 응답이 불명확하면 같은 등록 ID를 GET 결과에서 먼저 확인한다. 새 ID로 무조건 재등록하거나 토큰 요청을 반복하지 않는다. 앱 사용자는 원문 키를 응답으로 다시 볼 수 없고, 암호화된 봉투도 응답에 포함하지 않는다.

선택 이전에는 지원 계좌의 최소 매핑만 암호화해서 보관한다. 선택이 끝나면 **선택한 계좌 하나의 매핑만 남기고** 나머지 매핑은 버린다. 실제 종목 조회·스냅샷은 선택한 계좌만 대상으로 한다. 다른 계좌로 바꾸려면 해제 후 새 연결을 만들고 다시 선택한다.

GET은 활성 구성원의 본인 연결만 허용한다. 쓰기는 owner/admin/member 역할을 요구하지만 가족 관리자라고 다른 사람의 연결을 수정할 수 없다. viewer로 바뀌면 DB 트리거가 기존 접근 자료를 즉시 폐기한다. 서버는 멤버십 ID와 정확한 `joined_at`을 함께 확인한다. 탈퇴·재가입으로 과거 동의가 되살아나지 않는다.

## 발급·갱신·경합 규칙

1. 공급자 I/O **전** 연결/요청 claim을 DB에 커밋한다. 활성 클라이언트 지문의 고유 인덱스가 API 인스턴스·가족·사용자 사이의 중복 발급 주체를 차단한다.
2. 기존 공급자 만료 시각이 실제로 지났고 이전 발급이 확정 완료된 ready/error 연결만, 다음 사용자 조회 요청 안에서 한 번 갱신한다. 만료 30초 전부터는 그 만료 시각까지 새 조회를 기다린다. 갱신 후 암호화 토큰을 저장한 뒤 선택 계좌를 읽는다.
3. 공급자 401/외부 토큰 교체는 `reauth_required`로 처리하며 자동으로 재발급하지 않는다. 토큰 요청 timeout/5xx/성공 응답 파싱 실패처럼 발급 여부를 알 수 없는 경우는 `token_uncertain`이다. 원문 응답·오류·키를 로그나 API 오류에 넣지 않는다.
4. `token_issuance=started/uncertain`인 기록은 **연결 해제 후에도** 클라이언트 고유 발급 권한을 잡아 둔다. 늦은 기존 발급이 새 토큰을 무효화할 수 있기 때문이다. 확실히 발급하지 않은 조기 종료만 complete로 정리한다. 불명 발급에는 새 공급자 클라이언트 ID를 발급받는 흐름이 필요하며 DB 잠금을 지우는 수동 우회를 하지 않는다.
5. 외부 호출 전·결과 저장 전 권한/멤버십/operation ID/version을 다시 확인한다. 해제·탈퇴·재가입 이후 늦은 응답은 저장되지 않는다. 이미 전달한 금융사 요청을 취소하거나 공급자 토큰을 폐기했다고 보장하지 않는다.
6. 연결 해제는 version 상한에서도 동작하도록 증가를 포화시킨다. 새 조회는 claim과 완료에 필요한 두 버전을 외부 I/O 전에 확보할 수 있을 때만 시작한다. 버전 고갈 때문에 토큰 발급만 되고 완료를 기록하지 못하는 경로를 막는다.
7. 90초 넘게 남은 작업은 GET에서 불명 상태로 표시한다. GET 자체가 claim을 해제하거나 작업을 다시 실행하지 않는다.

`Retry-After`는 [RFC 9110 §10.2.3 및 §5.6.7](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3)의 비음수 정수 초와 HTTP-date(구형 날짜 형식 포함)를 읽는다. 초 미만은 올림하여 이르게 조회하지 않는다. 유효하지 않은 값은 원문을 저장/반환하지 않는다. RFC에 초 수 상한이 없으므로 매우 큰 유효 값은 4자리 연도로 표현 가능한 마지막 시각인 9999-12-31에 보수적으로 고정한다. 임의로 60초나 하루로 줄이지 않는다. 대기 중 GET/화면 재진입은 공급자 호출을 시작하지 않으며 새 타이머를 만들지 않는다.

## 보관과 암호화

0067은 `finance_connections`와 `finance_connection_snapshots` 두 테이블을 추가한다. 후자는 요청 멱등성과 관측 증거를 함께 보관하며 pending에서 succeeded/failed로 한 번만 전이할 수 있다. terminal 기록은 수정/삭제를 거부한다. 실패가 마지막 성공 관측 포인터를 덮지 않는다.

AES-256-GCM은 이 기능 전용 버전별 키를 사용한다. AAD에는 앱 소유자·공급자·연결 ID·용도(credentials/token/accounts)·키 버전을 묶는다. SMS 장치용 키나 MCP 세션 키를 재사용하지 않는다. IV는 매번 새로 만들고 이전 버전의 복호화 키는 계획된 교체 동안 유지해야 한다. 키 분실은 자동 복구/새 키 대체로 숨기지 않는다.

**연결 해제는 과거 관측의 영구삭제가 아니다.** 암호화 접근 자료는 폐기하고 이전 관측은 보관하되 연결 화면에서는 숨긴다. 원문 키나 금융사 세션을 보관한 감사 로그는 없다. 관측 보존 기간 및 영구 삭제 절차는 이 버전에서 새로 정하지 않았다. 실제 활성화 전 이 보관 방식을 사용자에게 설명하고 기존 개인정보 삭제 정책과의 정합성을 확인해야 한다.

회원 제거, viewer 전환, 재가입 시각 변경, 사용자/가족 soft-delete는 0067의 DB 트리거가 접근 자료를 폐기한다. 0067을 모르는 이전 앱 버전으로 롤백해도 이 방어는 DB에 남긴다. 마이그레이션 역삭제로 롤백하지 않는다. 기존 가족 합계·공유 정책을 확대하는 트리거는 없다.

## 운영 활성화 전 별도 준비

소스 설정만 추가했으며 실제 운영 값은 읽거나 만들지 않았다.

- `FINANCE_CONNECTIONS_ENABLED`: 기본 false.
- `FINANCE_CONNECTION_VAULT_ACTIVE_VERSION`: 운영자가 선택한 활성 키 버전.
- `FINANCE_CONNECTION_VAULT_KEYS_JSON`: 전용 32바이트 키의 버전별 JSON 매핑. 최대 8개. 실제 값은 채팅·소스·명령행 인자·로그에 남기지 않는다.

설정이 없으면 공급자 접근은 비활성이다. 활성 상태인데 키가 누락/잘못됐으면 일반 오류로 시작을 거부한다. 운영 활성화에는 전용 키 생성/안전한 보관·복구·교체 경로에 대한 구체적 운영 승인, 공급자 조건 확인, 승인된 마이그레이션·배포 절차가 필요하다. 이 코드는 실행 중인 설정 파일이나 소켓/보안/IP 설정을 바꾸지 않는다.

실제 계좌 연결은 사용자가 정상 로그인한 앱의 입력 화면에 새 키를 직접 넣는 경로만 사용한다. 과거 채팅에 노출된 키는 쓰지 않는다. 공급자 약관은 본인이 확인/수락한다. 조회와 앱 저장 동의는 가족 공유 동의가 아니므로 초기 버전에서는 공유 스위치를 제공하지 않는다.

## 검증 상태와 남은 필수 검사

이번 하위 작업에서 어댑터·vault·설정·계약·상태 정책·서비스 회귀 테스트를 작성했다. **테스트/컴파일/빌드/DB 검증은 실행하지 않았다.** 이전 리뉴얼 검증 결과를 이 변경의 통과로 재사용하지 않는다. 서비스 단위 테스트의 DB는 스크립트형 합성 경계이며 실제 PostgreSQL 잠금/트리거 검증을 대신하지 않는다.

루트의 자원 제한을 지킨 순차 검증에서 다음을 확인해야 한다.

- config/contracts/database 빌드 후 API·web 타입 검사, 관련 단위/계약/구성 테스트, 필수 아키텍처 게이트, 웹/앱 빌드.
- 격리 PostgreSQL의 정확한 0067 적용: 같은 클라이언트 동시 등록, 같은 요청 동시 갱신, 정상 만료 1회 발급, 불명 발급 해제 후 중복 차단, claim/완료 롤백, terminal 스냅샷 불변성.
- 실제 HTTP/JWT 경로의 비회원/다른 소유자/viewer 거부, 멤버십 microsecond 경계, 탈퇴·재가입·사용자/가족 삭제와 진행 중 응답 경합. 구버전 동작에서도 DB 트리거로 접근 자료가 폐기되는지 검증.
- 연결 해제 INT_MAX, 새 조회 max-1 사전 차단, 32,768자 토큰, 음수·소수·Number 안전 범위 초과 값, KRW/USD 분리, 계좌 선택·실패 시 마지막 성공 값 보존. 공급자 429/503의 120초 대기가 기본 60초 후에도 유지되는지, HTTP-date/큰 지연값/실패 전후 시도 시각 보존도 확인한다.
- 등록 화면 비밀 미보관/미로깅, 반복 클릭·닫기·늦은 응답·결과 불명 조회, 기기별 레이아웃, 가족/사용자 변경 시 화면 잔류 데이터 정리.
- 설정 false인 운영 후보의 기능 비활성과 기존 기능 회귀. 실제 금융사/실제 계좌/실제 키 입력은 별도 준비가 완료된 뒤에만 확인.
