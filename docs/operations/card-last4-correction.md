# 카드 뒤 4자리 정정

카드 관리의 ‘뒤 4자리 정정’은 기존 카드 한 건의 번호 표기를 바로잡는 기능이다.
일반 편집과 신규 등록을 호출하지 않으며 기존 거래를 소급 연결하거나 재처리하지 않는다.
카드 ID·소유자·별칭·공개 범위·공용 여부·상태·생성 시각을 유지한다. 실제 변경은
`payment_cards.masked_number`와 일반 수정 시각 `updated_at`뿐이다.

## API와 권한

`PATCH /v1/cards/:id/last4`는 정상 사용자 인증을 요구한다. 활성 가구 구성원 중 카드
소유자 또는 owner/admin만 허용한다. 요청은 다음 세 항목만 허용하는 strict 계약이다.

```json
{"last4":"0001","expectedLast4":"0000","expectedOwnerMemberId":"10000000-0000-4000-8000-000000000001"}
```

`last4`는 ASCII 숫자 정확히 4개이며 앞자리 0을 보존한다. 기존 번호가 없으면
`expectedLast4`는 `null`이다. 전체 카드번호·추가 필드·다른 형식은 받지 않는다.
`expectedOwnerMemberId`는 화면에서 확인한 소유자 UUID를 비교하는 전제이며 소유자를
변경하는 필드가 아니다. 잠긴 실제 소유자가 다르면 관리자도 409로 보류한다.
응답은 기존 `CardSummary`이다. 이미 같은 번호라면 권한과 소유자 전제를 확인한 뒤 쓰기 없이 성공한다.
이 경우 오래된 expected 값을 가진 응답 유실 재호출도 안전하다.

다른 번호로 바꾸려는데 현재 번호가 expected와 다르면 409 `card_last4_stale`로 보류한다.
장식 제거 후 숫자 정확히 4개인 기존 마스킹만 이해하며, 비정상 형식이나 전체 번호를
끝 4자리로 잘라 추정하지 않는다. 화면도 원래 번호 전체를 표시하지 않는다.

## 충돌과 잠금

활성 대상 카드에서는 같은 가구의 활성 카드 중 발급사·뒤 4자리가 정상 자동 연결
규칙으로 일치하고, 소유자가 같거나 어느 한쪽이 공용이면 409 `card_last4_conflict`로
보류한다. 서로 다른 개인 소유자의 카드는 구분한다. 불명확한 기존 식별 정보로 겹침
여부를 추정하지 않는다. 비활성 대상은 현재 자동 연결에 참여하지 않는다.

초기 권한 확인 후 READ COMMITTED 트랜잭션에서 가구 행 FOR UPDATE → 활성 호출자 멤버십
FOR SHARE NOWAIT → 가구 카드 ID 순 FOR UPDATE NOWAIT로 잠근 뒤 권한·현재값·충돌을 재확인한다.
가구 외래키 검사와의 잠금 충돌로 동시 신규 등록을 앞뒤로 순서화한다. 정상 신규 등록의
기존 정책과 소급 연결 동작은 변경하지 않는다. 정정 이후 별도 신규 등록까지 전역
유일성을 보장하는 기능은 아니다.

기존 승격은 카드 행을 먼저 잠근 뒤 거래의 가구 외래키를 검사할 수 있다. 정정이 가구
잠금을 가진 채 그 카드 행을 기다리지 않도록 NOWAIT를 사용한다. 필요한 멤버십·카드가
다른 쓰기에서 사용 중이면 잠금 실패를 안전한 409 보류로 반환하고 트랜잭션을 롤백한다.
자동으로 재시도하거나 기존 승격·등록 경로의 잠금 정책을 바꾸지 않는다.

## 화면과 실제 정정

정정 화면에서 소유자·별칭·발급사·현재 뒤 4자리를 함께 확인한다. 동일 이름이나 여러
카드로 대상을 유일하게 확인할 수 없으면 저장하지 않고 필요한 식별 정보만 확인한다.
전체 카드번호나 문자 원문을 요청하지 않는다.

저장 실패 시 입력을 보존한다. 결과가 불명확하면 정상 조회로 현재 카드를 다시 확인한
뒤 판단하며, 같은 요청을 무조건 반복하지 않는다. 오래된 응답은 닫힌 화면이나 다른
가족 화면을 다시 열지 않는다. 미확정 상태는 같은 쿼리 클라이언트의 가구·카드별로 유지해
닫기·재오픈으로 사라지지 않으며, 미확정 발생 뒤 시작한 정상 GET 성공으로만 해제한다.
정정 후 처리하는 문자의 자동 연결에는 새 번호가 쓰이며,
이미 연결된 거래의 카드 ID나 금액·소유자는 정정 동작으로 변경하지 않는다.

실제 반영은 정상 앱 인증과 이 전용 API로만 수행한다. 임의 SQL·임시 관리자 코드·새 카드
등록을 대체 경로로 사용하지 않는다. 저장 후 카드의 새 번호와 원래 소유자·메타데이터를
정상 조회로 확인한다. 회귀 검증은 합성 데이터의 거래·예산·관련 이력 전체 불변을 비교한다.

## 배포 범위

DB 마이그레이션과 새 의존성은 없다. 기존 운영 이미지의 Linux 의존성을 유지하고,
검증한 공개 소스·계약·API 전체 산출물·운영 URL 웹 산출물만 고정 manifest로 복사한다.
Next의 cache/dev 제외 규칙을 API 등 다른 산출물에 적용하지 않는다. 전체 API와 worker
진입 모듈 해석, 격리 PostgreSQL, 필수 CI, 실제 브라우저 합성 검증을 통과한 후보만
정확한 이미지 ID로 반영한다. 기존 Compose/env 경로 순서를 유지하고 이전 이미지를 보존한다.

파서 유지보수 저장소·활성 설정·예약은 별도 승인 범위다. 이 기능 배포가 그 핸드오프를
대신하지 않으며, 예전 이미지·커밋·Compose 경로에 묶인 핸드오프 계획은 실행 전 새 운영
기준과 대조해야 한다. 운영 배포가 다른 작업의 변경을 관찰하면 덮지 않고 보류한다.
