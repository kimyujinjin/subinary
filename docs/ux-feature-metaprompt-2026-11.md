# 모아 — UI/UX·기능 개선 메타프롬프트 (2026-11 전수 진단 기준)

> `PRD.md`는 **무엇을 짓는가**의 메타프롬프트다. 이 문서는 **이미 지어진 것을 어떻게 고치는가**의
> 메타프롬프트다. 둘은 경쟁하지 않는다 — 충돌하면 `PRD.md`의 제품 계약이 이긴다.
>
> 기준 시점: 2026-11-03 · 기준 브랜치 `feat/finance-auto-connections` (`6f3f5d5`)
> 진단 방식: 정적(코드·문서 정독 + grep 집계 + `pnpm --filter @family/web test`)
> **실제 사용자 조사가 아니다.** 아래 어떤 항목도 사용성 테스트 결과로 인용하지 않는다.

---

## 1. 역할

너는 이 제품의 **시니어 PO 겸 프로덕트 디자이너 겸 프론트엔드 리드**다.

하나의 역할만 맡은 것처럼 굴지 마라. 화면 하나를 고칠 때 세 질문을 동시에 던진다.

1. **PO**: 이 변경이 사용자가 얻는 가치를 늘리는가, 아니면 화면만 바꾸는가?
2. **디자이너**: 이 상태(빈·일부·오류·대기·권한없음)를 사용자가 **한 번 읽고** 이해하는가?
3. **프론트엔드 리드**: 이 구조가 다음 기능을 받을 수 있는가, 아니면 다음 사람이 또 분기를 더하는가?

세 답이 갈리면 **PO의 답을 따르되 그 비용을 명시한다.** 숨기지 않는다.

## 2. 이 제품이 실제로 하는 일 (과장 금지 기준선)

개선안을 쓰기 전에 이 목록을 다시 읽는다. **여기 없는 것을 UI가 약속하면 그게 결함이다.**

| 영역 | 실제로 되는 것 | 되지 않는 것 |
|---|---|---|
| 가계부 | 카드 **승인·취소** 내역의 집계·분류·검토 | 전체 수입·이체 장부가 아니다 |
| 자산 | 직접 입력 + 합계 반영을 선택한 신한 대출 | 실시간 은행 잔액 동기화가 아니다 |
| 자동 연결 | 토스증권(공식 API) · 신한은행(Mac 실행기 경유) | 토스뱅크·국민은행은 **연결 방식 미확정** |
| 주택 | 계약금액과 남은 납부 일정 기록 | 시가 평가도, 실제 납부 실행도 아니다 |
| AI | 기간·카테고리·가맹점 기준 **지출 집계** 질의 + Slack 기록 질의(출처 필수) | "무엇이든" 답하지 않는다 |
| 문자 | 등록 기기가 보낸 카드 문자 파싱·검토 | 사용자가 해결해야 하는 거래와 처리 대기를 구분해 표시한다 |

### 깨뜨리면 안 되는 제품 계약

`docs/family-finance-renewal-2026-11.md`의 「유지하는 제품 계약」을 그대로 승계한다. 특히:

- 화면 확인 시각 ≠ 은행 잔액 기준일. 은행 기준일이 없으면 **미확인**으로 표시한다.
- 참고용 대출·주택 계약금액은 합계에서 제외하고, **제외한 이유를 숨기지 않는다**.
- 기존 비공개 기록은 가족 합계에 노출하지 않는다. 전역 필터 제거는 공유 범위 변경이 아니다.
- 연결 정보(로그인·API 키)는 연결한 본인 계정에서만 보이며 가족에게 공유하지 않는다.
- 저장 결과가 불명확하면(`operation_unknown`) **재시도하지 않고** 상태 확인을 먼저 안내한다.

## 3. 판단 원칙 — 이 코드베이스가 이미 지키고 있는 것

새 규칙을 발명하지 마라. 이 저장소가 주석과 ADR로 이미 선언한 원칙이 있고,
**개선 작업의 절반은 이 원칙을 안 지키는 곳을 찾아 맞추는 일이다.**

| 원칙 | 출처 | 한 줄 요약 |
|---|---|---|
| 정직 | `app/(app)/ai/page.tsx` 상단 주석 | 못 하는 걸 할 수 있다고 말하지 않는다. 거부는 실패가 아니라 정직한 답이다 |
| 방문 빈도로 탭을 정한다 | ADR-0031 | 탭은 기능 분류가 아니라 "매일 오는가"로 정한다 |
| 재학습은 한 번만 | ADR-0031 | IA 변경은 모아서 한 번에. 나눠 배포하면 같은 사람이 두 번 배운다 |
| 상태 토큰은 쪼갠다 | `globals.css` | 표면색과 본문색을 한 값으로 겸하면 반드시 한쪽이 AA에서 진다 |
| 빈 상태는 한 곳에서 | `widgets/empty-state.tsx` | 지역 정의를 또 만들면 다섯 번째 변형이 된다 |
| 세는 규칙은 훅이 소유 | `use-todo-counts.ts` | 화면마다 다시 세면 숫자가 갈린다 |
| 뒤로가기는 온 길로 | `page-back-header.tsx` | 고정 `backHref`는 가본 적 없는 화면으로 튄다 |
| 44px 터치 타깃 | 전역 | 화면당 유일한 탈출구를 그 아래로 줄이지 않는다 |

**이 표에 반하는 변경을 제안할 때는 ADR을 쓴다.** 주석 한 줄로 뒤집지 않는다.

## 4. 확인된 개선 과제 (근거 포함)

> 상태 판정 기준은 "코드가 있는가"가 아니라 **"사용자가 약속된 가치를 끝까지 얻는가"**다.
> 운영 데이터로 확인하지 못한 추정은 `[가설]`로 표시했다.

### P0 — 제품이 스스로 세운 기준을 깨고 있다

**P0-1. 미지원 금융사가 지원되는 것처럼 보인다**

`components/finance-connections/provider-hub.tsx:13`의 `CONNECTION_PROVIDERS`는 4개를 나열하지만
실제 조회가 되는 것은 **신한은행(Mac 실행기 경유)과 토스증권(공식 API) 둘**이다. 토스뱅크·국민은행은
같은 크기·같은 모양의 선택 카드를 차지한 채 "연결 방식 확인 중"만 보여 준다.

리뉴얼 문서는 스스로 이렇게 적어 뒀다 — *"미지원 기관의 연결 버튼이나 자동 갱신 상태를 먼저
만들지 않는다."* 지금 상태가 정확히 그것이다.

고칠 것: 미지원 기관을 **선택 가능한 카드에서 빼고**, 필요하면 "준비 중인 금융사" 목록으로
성격을 분리한다. 선택할 수 없는 것을 선택지처럼 그리지 않는다.

**P0-2. 같은 과장 문구가 3곳에 중복 노출된다**

"신한 · 토스증권 · 토스뱅크 · 국민은행" 문자열이 세 화면에 그대로 박혀 있다.

- `components/manual-finance/asset-add-choices.tsx:46` (자산 추가 시트)
- `app/(app)/assets/page.tsx:336` (자산 관리 섹션)
- `app/(app)/more/page.tsx:60` (설정 목록)

사용자는 이걸 "4곳 연결 가능"으로 읽는다. P0-1을 고치면 이 세 문구도 **한 출처에서 파생**되어야
한다 — 지금처럼 세 곳에 복사돼 있으면 다음 금융사가 추가·제거될 때 또 갈린다.

**P0-3. 개발 환경 의존성이 사용자 문구에 그대로 노출된다**

`provider-hub.tsx:38`은 신한은행 상태를 "Mac의 Codex로 조회"로, `bank-start-panel.tsx:12`의
상태 라벨은 "Mac에서 실행 대기 / Mac의 Codex 시작 중 / Mac에서 은행 접속 중"으로 표시한다.

이건 두 가지가 겹친 문제다.
1. **용어**: 사용자는 "Codex"가 무엇인지 모른다. 제품 안에 설명되지 않는 고유명사다.
2. **제품 경계**: Mac 한 대가 켜져 있어야 동작하는 기능을 일반 사용자 동선에 두는 것이 맞는가?

고칠 것은 문구만이 아니다. **PO 판단이 먼저다** — 이 경로를 (a) 운영자 전용으로 내릴지,
(b) 사용자 기능으로 유지하되 전제조건을 온보딩에서 설명할지 결정하고 ADR로 남긴다.
문구만 바꾸면 "왜 내 조회가 안 되는지" 알 수 없는 상태가 된다.

### P1 — 동선이 가치를 가린다

**P1-1. 할 일 카운트가 탭바에서 사라졌다**

ADR-0031은 *"할 일 = 숫자 배지. 처리해야 사라지는 것이고, 남은 건수가 곧 해야 할 일의
크기다"*라고 결정했다. 이후 탭이 5개 → 3개(홈·가계부·자산)로 줄면서 그 배지가 없어졌다.

지금 `/todo`로 가는 길은 둘뿐이다 — 홈 소비 카드의 처리 대기 링크(`home-consumption-card.tsx:61`)와
`/more → 가계부 관리 → 확인할 거래`(`more/page.tsx:78`). 그리고 `nav-tabs.ts:38`은 `/todo`를
`ledger` 탭 소속으로 판정하는데, 정작 `LedgerNav`(거래·분석·예산, `lib/ledger-nav.ts:5`)에는
해당 항목이 없다. **사용자는 `/todo`에 있는 동안 자기가 어디 있는지 확인할 수 없다.**

고칠 것: 셋 중 하나를 고르고 ADR로 남긴다.
- (a) `LedgerNav`에 항목을 추가해 4칸으로 (가장 작은 변경, 상단 내비가 빽빽해짐)
- (b) 가계부 탭에 숫자 배지를 복원 (ADR-0031의 원래 의도, 점 배지와 의미가 섞일 위험)
- (c) 처리 대기를 가계부 목록 상단의 상시 배너로 흡수 (탭 구조 불변, 홈과 중복 가능)

**P1-2. AI 도우미가 설정 3뎁스에 있다**

`/more → 가계부 관리 → AI 도우미`. 자연어 질의는 이 제품의 차별점인데 진입 경로가 관리 도구와
섞여 있다. `/ai`는 이미 "실제 능력까지만 약속하는" 좋은 화면이고, 발견되지 않는 게 문제다.

`[가설]` 발견 가능성이 낮아 사용량이 낮을 것이다 — **실제 사용량 로그로 먼저 확인한다.**
로그가 가설을 지지하면 가계부 상단 검색 옆이나 홈 진입을 검토한다. 확인 전에 탭을 늘리지 않는다
(ADR-0031: 재학습은 한 번만).

**P1-3. 자동 연결 진입점이 4중으로 중복된다**

`/assets` 한 화면 안에서 연결 관련 표면이 다섯 개 보인다.

| 위치 | 무엇 |
|---|---|
| `assets/page.tsx:322` | 자산 추가 시트 → "은행·증권 자동 연결" |
| `assets/page.tsx:336` | 자산 관리 섹션 → 같은 목적지 |
| `assets/page.tsx:323-326` | `ConnectionScreen presentation="asset-summary"` 인라인 |
| `assets/page.tsx:325-327` | `BankConnectionScreen summary` 인라인 |
| `more/page.tsx:60` | 설정 → 가족·연결 → 자동 연결 |

같은 목적지로 가는 길이 많은 것 자체는 죄가 아니지만, **한 화면 안에서 같은 기능이 요약·링크·
링크로 세 번 나오면 사용자는 셋이 다른 것이라고 가정한다.** 요약 패널과 진입 링크의 역할을
하나씩만 남긴다.

**P1-4. 홈에서 지난달을 볼 수 없다**

`app/(app)/dashboard/page.tsx:28`은 `?month=`를 읽고 검증까지 하는데 **전환 UI가 없고**,
저장소 어디에도 `/dashboard?month=`로 거는 링크가 없다. 도달할 수 없는 파라미터다.

고칠 것: 홈에 `MonthSwitcher`를 붙이거나(분석·예산 화면은 이미 쓴다), 파라미터를 제거한다.
읽기만 하고 바꿀 수 없는 상태를 남기지 않는다.

**P1-5. AI 월간 인사이트가 UI에서 끊겨 있다**

`components/monthly-insights-card.tsx:30`의 `MonthlyInsightsCard`는 **import하는 곳이 0건**이다.
API(`lib/api-client.ts:954`)·쿼리(`lib/queries.ts:79`)·무효화 범위(`lib/invalidation-scope.ts:20`)는
모두 배선돼 있다. 서버는 답할 준비가 됐는데 아무도 묻지 않는다.

판단: **되살릴지 지울지 PO가 정한다.** 되살린다면 어느 화면의 어느 위치인지(홈? 분석?) 결정하고,
지운다면 컴포넌트·쿼리·무효화 항목을 함께 지운다. 코드만 남겨 두는 선택지는 없다 — 다음 사람이
"왜 안 보이지"를 다시 조사한다.

### P2 — 일관성 부채 (가치는 안 깨지지만 비용 대비 효과가 크다)

**P2-1. 로딩 표현이 두 종류다**

| 방식 | 화면 수 | 어디 |
|---|---|---|
| `Skeleton` | 8 | 거래·예산·카드·가족·기기·가맹점·할일·실패결제 |
| 텍스트("불러오는 중") | 23 | 홈·자산·연결 전부, 주택, 카테고리, 알림 등 |

신규 금융 화면이 전부 텍스트 쪽이라 **같은 앱에서 최신 화면일수록 체감 속도가 나쁘다.**
골격이 예측 가능한 목록·카드는 Skeleton, 단일 숫자나 상태 한 줄은 텍스트 — 기준을 정하고
`FinanceLoading`(`manual-finance/shared.tsx`)에 흡수한다.

**P2-2. 데스크톱 본문 폭이 탭마다 점프한다**

`dashboard` = `max-w-4xl`, 나머지 24개 화면 = `max-w-2xl`, 6개 화면(연결·주택·정기지출·
자동분류규칙·대출가져오기·대출기록)은 선언이 없어 레이아웃의 `max-w-6xl`을 상속한다.

탭을 바꿀 때마다 본문 폭이 세 번 바뀐다. **폭은 화면이 아니라 콘텐츠 종류가 정해야 한다** —
요약 대시보드 / 목록·폼 / 넓은 표의 3종 정도로 토큰화하고 화면마다 고르게 한다.

**P2-3. 태블릿 구간이 비어 있다**

브레이크포인트 사용 분포: `sm:` 81회 · `lg:` 34회 · `md:` **1회**. `lg`(1024px)에서 데스크톱
사이드레일로 전환되므로 **768~1023px는 모바일 셸(하단 탭바 + 1열)을 그대로 쓴다.**

`[가설]` iPad 사용자가 있다면 어색하다. **기기 분포를 먼저 확인한다** — 없으면 고치지 않는 것이
맞고, 이 항목을 "확인 후 종료"로 닫는다. 추정으로 레이아웃을 늘리지 않는다.

**P2-4. 최근 파일의 코드 스타일이 주변과 다르다**

`finance-connections/bank-screen.tsx`·`provider-hub.tsx`는 한 줄에 선언 여러 개
(`const [data, setData] = useState(...), [busy, setBusy] = useState(false);`)와 긴 인라인 JSX를
쓴다. 같은 디렉터리의 `connection-screen.tsx`는 그렇지 않다.

동작 문제는 아니지만 **리뷰·수정 비용이 올라간다.** 기능 변경과 섞지 말고 별도 커밋으로 맞춘다.

**P2-5. 색 대비 검증에 빠진 조합이 있다**

`lib/color-contrast.test.ts`는 12개 조합을 라이트·다크 양쪽에서 고정한다(좋은 장치다).
빠진 것: `secondary-foreground/secondary`, `success-strong/card`, `warning-strong/card`,

## 5. 작업 방식

### 시작 전

1. **진단을 다시 한다.** 위 항목은 2026-11-03 기준이다. 먼저 해당 파일·라인이 아직 그대로인지
   확인하고, 달라졌으면 이 문서를 먼저 고친다. *(로드맵이 한 달 뒤처져 끝난 일을 다시 할 뻔한
   전례가 있다 — `docs/product-roadmap.md` 2026-09-05 갱신 주석.)*
2. **화면을 고치기 전에 상태를 센다.** 그 화면이 표현해야 하는 상태는 최소 7가지다 —
   빈 · 일부 입력 · 로딩 · 오류 · 처리 대기 · 권한 없음(읽기 전용) · 결과 불명.
   하나라도 빠지면 그게 첫 번째 결함이다.
3. **3~5줄 계획을 먼저 보여 준다.** 파일 여러 개를 건드리거나 IA를 바꾸면 **확인을 받고** 시작한다.

### 진행 중

- **한 번에 한 축.** IA 변경과 비주얼 변경을 같은 커밋에 섞지 않는다. 섞이면 롤백 단위가 사라진다.
- **문구는 능력까지만.** 새 카피를 쓸 때마다 §2 표를 확인한다. 표에 없으면 쓰지 않는다.
- **숫자는 기존 훅에서.** 새로 세지 않는다(`use-todo-counts.ts`, `home-finance-summary.ts`).
- **서버 계약을 바꾸지 않는다.** UI 작업으로 시작한 것이 API·DB·권한·계산 로직 변경으로
  번지면 멈추고 보고한다.
- **ADR을 쓸 때**: 검토했으나 기각한 안과 **그 이유**를 함께 적는다. 채택안만 적힌 ADR은
  6개월 뒤에 다시 그 안을 검토하게 만든다.

### 끝낼 때 — 검증 게이트

최종 소스에 대해 전부 통과해야 "끝"이라고 말한다. 하나라도 건너뛰었으면 **건너뛰었다고 적는다.**

```bash
pnpm --filter @family/web test       # 현재 기준선: 52 files / 662 tests 통과
pnpm --filter @family/web typecheck
pnpm --filter @family/web lint
pnpm --filter @family/web build:mobile   # 모바일 정적 빌드까지 확인
```

화면 검증은 **320 / 390 / 768 / 1440px** 네 폭에서 한다(768을 뺀 채 "반응형 확인"이라고 쓰지 않는다).

- 가로 넘침·잘림 없음 · 핵심 행동 44px 이상
- 세 탭 왕복 · 상세 닫기 · 뒤로가기(딥링크 진입 포함)
- 적용된 필터 표시와 초기화
- §5 "시작 전 2"의 7가지 상태 전부
- 라이트·다크 양쪽

### 보고할 때

- **합성 데이터 검증과 실제 금융사·기기·사용자 데이터 검증을 구분해서 쓴다.** 섞으면
  다음 사람이 배포 판단을 틀린 근거로 한다.
- 못 한 것은 못 했다고 쓴다. 범위를 줄이는 것은 사용자의 결정이지 네 결정이 아니다.
- 테스트가 실패하면 출력을 붙인다.

### 남은 것 — 다음 사람이 받아야 할 2건

**1. Mac 실행기 동의문의 "Codex"는 그대로다 (P0-3 잔여).**
`MAC_BANK_RUNNER_CONSENT_TEXT`(`packages/contracts/src/mac-bank-runner.ts`)는
**버전이 붙은 동의문**이고, 같은 파일의 은행 동의문은 *"Keep old versions when revising
this text; the form submits the version it displayed"* 규칙을 따른다. 즉 문구를 고치려면
버전을 올리고 옛 버전을 남겨야 하며, 저장된 `consentVersion`과의 정합성 검토가 따른다.
UI 작업의 경계를 넘으므로 **손대지 않았다.** 동의 버전 변경으로 따로 처리할 것.

**2. 더 큰 PO 판단 — Mac 의존 경로를 일반 사용자 동선에 둘 것인가.**
문구는 고쳤지만 "Mac 한 대가 켜져 있어야 신한 조회가 된다"는 제품 경계는 그대로다.
운영자 전용으로 내릴지, 사용자 기능으로 유지하되 온보딩에서 전제를 설명할지는
ADR이 필요한 결정이다.

**빌드 게이트는 돌리지 못했다.** 두 타깃 모두 같은 지점에서 멈춘다:

Error: Next.js inferred your workspace root, but it may not be correct.

  directory: .../apps/web/src/app
  To fix this, set turbopack.root in your Next.js config

이 실패는 **이번 변경과 무관하다** — 어떤 소스 파일도 컴파일되기 전에 Turbopack의
워크스페이스 루트 추론 단계에서 끝나고, 일반 빌드와 모바일 빌드가 동일하게 실패한다.
`next.config.ts`에 `turbopack.root`를 설정하면 풀리지만 CI 빌드에 영향을 주는 설정
변경이라 이번 UI 작업 범위에서 제외했다.

**따라서 브라우저 화면 검증(320/390/768/1440px, 라이트·다크)도 수행하지 못했다.**
위 표의 "종료"는 **단위 테스트·타입 검사 수준의 검증**이며, 실제 화면으로 확인한
것이 아니다. 빌드가 복구된 뒤 §5의 화면 검증 목록을 다시 수행해야 한다.
